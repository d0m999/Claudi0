# PLAN — 产品体验优化讨论稿

## 五页设置修订（现行 · 2026-10-23）

本节取代历史八页／六页设置清单与快捷键交付合同。可见侧栏固定为：**工作区、声音包、连接、提醒与静音、通用**；前四项与通用以间距分组，无分组标题。画面唯一 SoT 是 [主原型](<../designs/panel-and-settings/Panel and Settings Prototype.html>)；首启讨论原型只保留未决首启对照和主原型链接。

- `SettingsDestination` raw values 保持兼容；侧栏、方向键与焦点顺序统一使用五页投影。`usage` 是实际活动与诊断正文，从连接页常驻入口进入，侧栏高亮连接；正文提供返回连接，工具栏保留真实历史和阅读位置。
- 显式 `about` 请求规范化为通用，由 `SettingsPresentationSession` 展示原生附属表单，不形成独立历史目的页。关闭／Esc 回到通用的关于入口；模态期间阻断外层导航，导航 stamp 拒绝迟到关闭。恢复旧 `about`／`shortcuts`／`display` 值时只投影通用，不自动弹关于、不报损坏、不改写旧字节；`usage` 可恢复。
- 工作区列表进入同窗口完整详情；摘要、声音配置与适用来源来自现有配置 owner。事件的“编辑包内声音…”／“查看包内声音…”进入声音包并定位事件，保留返回工作区入口、捕获写目标、失效拒写和删除确认。
- 声音包保留列表→详情、内置只读、收藏上限四个、草稿、导入、生成记录及全部失败态。服务与凭据入口收为紧凑管理项。AI 状态继续由 `AICueGenerationCoordinator` 拥有，遵循 ADR 0026；生成中、保存中、待处理、已保存与请求失败分别呈现。关闭只结束采用上下文；保存失败不解除新生成限制；重试保存不重复生成；放弃按实际剩余数量确认，废纸篓失败保留剩余结果及限制。
- 连接首页只呈现产品、开关、自然语言状态及详情入口。全应用活动诊断与宿主连接诊断分别保留；能力、回执和技术信息在宿主详情／诊断中。
- 提醒与静音依次为自动静默、横幅提醒、事件动画；接收器与快照健康按需展开，实际权限与失败保留恢复动作。通用依次为语言、登录项、软件更新、关于。关于只承载身份、版本／系统、资源与安全诊断摘要。
- 全局快捷键专用模型、Carbon 热键注册、动作派发、设置视图、fixture 与专用测试退役；旧偏好不读取、不注册、不删除。共享原生键盘导航、Zed 导航所需 Carbon 常量及窗口 handback 保留。

本轮不包含首启实现、设置搜索、Dock 入口、最近事件／为什么没响、真实 Provider 请求或发布。源码通过 Git 回退，不以删除用户配置、生成记录或音频回退；不保留源码备份。迭代运行受影响 suite，最终门禁不削弱；干净 HEAD 门禁须待精确范围本地提交获授权后执行。原生、自动、外部与发布证据分别记录于 [五页设置验收单](../docs/validation/five-page-settings-2026-10-23.md)。

## 0. 判断与原则

Claudio 的视觉规范、对比度、焦点、错误语义和证据体系已经明显高于同类工具。当前体验瓶颈主要不是「界面不够精致」，而是：

1. **内部领域模型泄露到主界面**：Surface、Binding、Receipt、当前激活等概念对维护者精确，对首次使用者过重。
2. **两个关键用户时刻没有被设计**：第一次使用时如何听到价值；日常使用时如何知道「为什么没响」。
3. **设置面的导航权重与使用频率不匹配**：八页等权并列，让一个小工具显得比实际更重。

本讨论稿遵循以下原则：

- 不新增第二个事实 owner，不新增第二条写入路径。
- 不伪造激活：示例试听、静态配置、测试通过都不得被呈现为真实宿主回执。
- 保留现有 typed route、稳定 raw value、窗口焦点 handback 与 64 条窗口期历史。
- 先做可回退、低风险的层级调整，再讨论需要 ADR 修订的页面合并。
- 所有新增 UI 文案必须有 English 与 `zh-Hans` 对应条目，并注册到 `ClaudioL10nKey.allKnown`。

## 2. §1 首次运行（讨论中）

### 2.1 现状证据

- `gui/Sources` 中没有独立的 onboarding / welcome 视图文件；首次启动主要执行 `SharedRuntimeBootstrap`，用户看到的是菜单栏图标与可打开的面板。
- `GlobalShortcuts` 已定义 `togglePanel` / `openSettings` / `openCurrentScopeEvents` 三个动作，但没有播种默认快捷键；`restorePersistedRegistrations()` 只恢复用户已保存的值。
- 应用为 `.accessory`，没有 Dock 图标。菜单栏图标被刘海、收纳或第三方菜单栏工具遮挡时，用户没有第二个可见入口。
- 面板首次打开时直接进入操作态：声音作用域、五个事件、音量与活动概览，没有「先连接宿主」的分步引导。

### 2.2 用户问题

首次安装后的真实问题不是「设置项在哪」，而是：

1. 这个 app 现在在工作吗？
2. 我怎么听到它的声音？
3. 我怎么知道它真的接上了 Claude Code / Codex，而不是只写了一份配置？
4. 如果菜单栏图标找不到，我还能怎么打开它？

### 2.3 目标

- 首次打开后 **10 秒内**能听到至少一个事件示例。
- **3 分钟内**能完成一个宿主的连接尝试，并理解「配置已写入」与「收到真实回执」的区别。
- 不产生任何伪造回执、伪造激活或伪造「已连接」状态。
- 键盘与 VoiceOver 用户能在不阅读 README 的情况下完成同一条路径。

### 2.4 可选形态

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| A. 面板内一次性引导 | 首次打开面板时挂一个 sheet / overlay，三步：试听示例 → 检测宿主 → 连接 | 不新增顶层 surface；复用现有面板与焦点体系；离用户第一次点击最近 | 空间有限；需要处理「关闭后如何再次进入」 |
| B. 独立首启窗口 | 单独一个 welcome window，承载更多说明与声音演示 | 空间充足，品牌感强 | 新增第三个顶层 surface；窗口生命周期、焦点 handback、关闭语义都要重新定义 |
| C. 空态即试听 | 不新增引导层；未接入时面板五事件行可直接试听，底部两行清单负责接入，菜单栏一次性指示兜底入口 | 无流程、无假等待；示例即时可听，接入由真实回执驱动；不新增 surface | 接入动作藏在清单里，发现性依赖卡片；展开宿主列表后面板需要滚动 |

**2026-10-22 决定**：先为 A（面板内引导）与 B（独立欢迎窗口）各做一版讨论原型；随后按「空态即试听」方向追加第三版 C，与 A/B 并列对照。三版都采用两段式完成标准，且都不包含快捷键步骤。C 不是原来的「仅空态清单」后备方案，而是对 A/B 向导形态的替代方向：面板不切换为流程，示例即时可听，接入由真实回执自己更新。

### 2.5 示例试听的语义边界

- 必须明确标注「示例试听，不代表宿主已接入」。
- 示例播放只读本地声音包，不写回执、不改配置、不点亮集成状态。
- 示例使用与真实播放一致的输出路径与音量语义；若音量过低导致听不见，应就地提示，而不是静默失败。
- 示例结束后，引导到真实连接；若检测到宿主已安装但未连接，直接定位到对应来源详情。
- 已完成真实回执后，不再自动展示示例。

**完成标准（2026-10-22）**：两段式。第一段在示例试听完成时结束；第二段只在收到至少一个宿主的真实回执时结束。用户可随时跳过第二段，但跳过不会被呈现为「已完成接入」。

### 2.6 快捷键与入口兜底（2026-10-22 决定）

- v1 不启用全局快捷键，删除快捷键设置模块；首启引导不包含快捷键步骤。
- 因此菜单栏图标成为唯一常驻入口。需要单独设计入口兜底：
  - 首次引导明确提示图标可能在菜单栏收纳区；
  - 评估「在 Dock 中显示」可选开关，或提供设置窗口内的「打开面板」动作；
  - 键盘-only 与 VoiceOver 用户依赖菜单栏状态按钮的无障碍入口，需要真机验证。
- 删除范围待实现时确认：至少移除设置页与导航入口；若整个 Carbon 注册链不再有消费者，应一并删除，避免死代码。

**原型观察（2026-10-22）**

- A 在 312×560pt 内可以容纳三步；步骤 1 的五事件列表与步骤 2 的宿主列表都不需要滚动。
- A 的主要风险是 transient popover：点击面板外部会关闭，首启流程可能被中断；需要定义「继续设置」入口。
- B 的空间足以把五种声音与「配置写入 ≠ 已接入」讲清楚；代价是新增第三个顶层 surface。
- 两种形态都能承载两段式完成标准；差异主要在入口、空间和窗口生命周期，不在流程内容。
- C 不切换面板内容：五个事件行在首启与日常状态完全一致，示例试听与真实播放共用同一行语义；第一行用一次性脉冲提示，不自动出声。
- C 的接入清单可随时收起，收起后保留一条「继续」入口；菜单栏指示只出现一次，作为图标被收纳时的入口兜底。
- C 初次展示无需滚动；宿主列表改为紧凑 2×2，最多显示 4 个已检测到的宿主；超过后「查看全部」下钻设置「连接」页，面板不再承担全量目录。
- C 的等待态统一为琥珀色，绿色只保留给真实回执后的「已接上」；A/B 的写配置态也从绿色改为琥珀色「已写入」，避免把配置写入误读为接入。
- C 的状态变化由真实回执事件驱动；原型中的「模拟回执」只是演示按钮，生产实现不应出现「重新检测」或需要用户手动推进的步骤。
- 同类产品研究见 §2.9；C 已补持久跳过与「菜单栏指示 / 临时 Dock」对照。

### 2.7 待讨论问题

1. 首启引导由「应用启动」触发，还是由「第一次打开面板」触发？倾向后者，避免无意图弹窗。C 的菜单栏指示可能需要在应用启动时出现，需单独决定。
2. 示例声音自动播放，还是必须点击「播放示例」？倾向点击，尊重用户当前音量与环境。C 已采用点击试听 + 首行脉冲，未自动播放；这一取舍是否成立？
3. 已决定：首启只列 `availability == .available` 且至少有一个可听事件的宿主；设置「连接」页保留完整目录与「未安装」状态。
4. 面板内引导是否违反「两个顶层 surface」的既有原则？需要确认它是否被视为面板的一部分。
5. 删除快捷键后，菜单栏图标被遮挡时的兜底入口选「临时 Dock」还是「设置窗口内打开面板」？C 原型已把「菜单栏指示 / 临时 Dock」做成对照；研究倾向临时 Dock，但需确认它是否改变菜单栏-only 身份。
6. 独立欢迎窗口（B）是否需要 modal、是否在应用启动时自动展示、关闭后如何再次进入？
7. C 的两行清单是否是必要的脚手架，还是可以进一步去掉，只保留菜单栏指示与空态试听？
8. 已决定：面板只显示已检测到的短列表与各宿主覆盖率；超过 4 个显示「查看全部」，完整连接、诊断和「重新检测」都在设置「连接」页。
9. 清单收走后，未接入状态如何长期保留而不重新变成任务？例如只在面板底部保留一行状态，或只在用户再次点开时出现。
10. 首启持久状态的正式 owner 是什么？原型用 localStorage 只是演示；需要与现有设置偏好或 UI 状态 owner 对齐，不能写入领域配置，也不能用它冒充接入。
11. 持久 dismissed 后，安静入口放在面板底部还是设置「连接」页？

### 2.8 验收边界

- 全新安装、无 `~/.claudio/` 配置、所有宿主都未连接时，能完成首启路径。
- 首次刷新未完成时显示「正在检查已安装的宿主」，不得提前断言「没有宿主」。
- 无宿主时示例试听仍可用；不写 `completed`，不循环打扰；设置保留「连接」入口。
- 宿主覆盖率来自快照（`supportedCount / totalCount`），不写死 5/5；没有可听事件的宿主不出现在首启可连接列表。
- 示例试听不产生 receipt、不改变 `config.json`、不点亮集成状态。
- 真实宿主事件产生真实回执后，首启状态正确结束。
- 键盘-only 与 VoiceOver 路径分别人工验证。
- 菜单栏图标不可见时有明确的找回路径。
- 卸载重装、升级安装、已有配置的用户不会被重复打扰。
- 关闭或跳过后，重启与升级不重放首启；设置中保留再次进入的入口。
- 若采用临时 Dock，只在首启未完成时出现，完成后回到菜单栏-only。
- 首启持久状态有明确 owner；不写入领域配置，不参与接入判定。

### 2.9 同类产品首启研究（2026-10-22）

**方法**：对照 8 个产品。MeetingBar、Ice、agentoast 直接阅读源码；CodexBar、Itsycal、Alfred、Raycast、OpenClaw 阅读公开文档与流程记录；另参考 NN/g 的空态与 onboarding 研究，以及 Apple HIG 的菜单栏规范。这里得到的是模式证据，不是 Claudio 的用户测试。

| 产品 | 首启形态 | 跳过 / 完成 | 更新后的处理 | 对 Claudio 的启示 |
|---|---|---|---|---|
| MeetingBar | 760×520 独立窗口；欢迎 → 来源 → 授权 → 选日历 → 常用设置 → 成功，4 段进度 | 关闭未完成窗口会退出 app；必须选来源和至少一个日历 | `onboardingCompleted` 只写一次；更新用 What's New 菜单项，不重放首启 | 只有接入是硬前置时才值得强制向导 |

| agentoast | 3 步独立窗口：欢迎 → 快捷键 → 接入 hooks | 接入可 Skip；Skip 与关闭窗口都写 `.onboarded` | 标记文件持久；完成后 `show_panel`；向导期间临时显示 Dock，结束回到 accessory | 最接近 C：跳过=完成、结束揭示入口 |
| CodexBar | 无向导；菜单栏图标 + Settings → Providers | 用户自行配置，权限按需触发 | 更新保留已有设置；新安装使用新默认 | 技术型用户可以 settings-first |
| Itsycal | 无 onboarding；菜单栏日历 + 齿轮设置 | 无完成状态 | 无首启；FAQ 解释图标被刘海/收纳隐藏 | 菜单栏入口发现性必须单独设计 |
| Alfred | Getting Started Assistant：授权、迁移、权限 | 许可步骤可跳过；权限可稍后授予，并在 General 重新请求 | 大版本迁移才走；不是每次更新 | 只放真实前置，提供再次进入 |
| Raycast | 欢迎 slides + 产品内 Welcome guide + 按需连接 | 迁移可跳过；文档说明可手动重跑 | v2 用 onboarding 承载迁移；不是每次更新 | 不要把 feature promotion 放进每次更新 |
| OpenClaw | 引导先验证一次真实 completion，再配置其余 | 失败显示错误/重试；摘要可关闭；权限按需 | 全新安装走自动引导；已有配置保留连接与行为 | 用真实结果作门槛，不用配置写入冒充成功 |

**共同模式**

1. **仪式感与依赖度匹配。** MeetingBar 不接日历就没有核心功能，所以强制向导合理；CodexBar、Itsycal 这类启动即用的工具没有首启向导。Claudio 的示例声音在未接宿主时也可用，因此 A/B 的向导仪式过重。
2. **跳过必须等于完成。** agentoast 把 Skip 和关闭窗口都写成 `.onboarded`，设置页保留完整接入入口。跳过不是失败，也不应在下次启动或更新后重放。
3. **首启与 What's New 分离。** MeetingBar 的首启完成标记只写一次，更新提示由独立版本标记和菜单项承载；Raycast 用 onboarding 承载 v2 迁移，而不是每次更新都重放。
4. **真实状态驱动。** Ice 按系统权限状态决定是否显示权限窗口；OpenClaw 必须通过一次真实 completion；MeetingBar 的完成接口校验来源与日历选择。没有假成功。
5. **结束时揭示入口。** agentoast 完成后调用 `show_panel` 展示菜单栏面板；agentoast 与 Ice 在首启或必要权限未完成时临时显示 Dock，结束或解决后回到 accessory。
6. **空态即引导。** NN/g 建议优先使用就地学习提示，空态说明「会有什么、怎么填满」，并直接给动作；示例内容要明确标注，不能让用户误以为是真实数据。
7. **复用同一套设置组件。** MeetingBar 首启的日历选择与 Preferences 使用同一套 grouped form；C 的宿主连接也应与设置「连接」页共用组件与语义。

**对 Claudio 的判断**

- A/B 借用了「接入是硬前置」产品的仪式：步骤条、进度点、完成页。Claudio 的价值在示例试听阶段已经出现，连接又是异步的，因此 A/B 的流程感与产品实际价值不匹配。B 的品牌宣言也接近 NN/g 所说的 feature promotion，容易像营销页。
- C 的方向被研究支持：空态即试听、就地动作、真实回执驱动状态。需要补齐三件事：
  1. **持久跳过 / 完成**：`unseen / dismissed / completed`；跳过写 `dismissed`，真实回执写 `completed`；更新不重置；已有配置或回执的用户升级后静默视为已看；设置保留「再看一次引导」。
  2. **入口兜底对照**：菜单栏指示 vs 临时 Dock。agentoast 与 Ice 证明临时 Dock 可行：只在首启或必要权限未完成时显示，完成或解决后回到 accessory。需要确认它是否改变 Claudio 的菜单栏-only 身份。
  3. **安静的重入口与组件复用**：清单收起后，在面板底部或设置「连接」页保留「接上宿主」；宿主选择与设置页共用同一组件。若面板内展开导致滚动，考虑改为下钻设置「连接」页。
- 更新语义：首启不按版本重放；现有用户在升级到带首启的版本时，只要有配置或回执就静默跳过；新功能用独立的 What's New 入口，不要重放整套首启。

**C 原型追加（2026-10-22）**

- 原型 C 已加入 localStorage 演示的持久状态：未看 / 已跳过 / 已完成；关闭清单写 `dismissed`，真实回执写 `completed`；「模拟重启」「模拟升级」不会重放已完成或已跳过的首启。
- 入口兜底可在「菜单栏指示 / 临时 Dock」之间切换；临时 Dock 只在首启未完成时出现，完成后隐藏；完成后面板底部显示「Claude Code 已接上 · 5/5」，并保留「最近一次事件会出现在这里」的空态说明。
- localStorage 仅用于讨论演示，不是生产持久化方案。正式实现前必须确认 UI 偏好 owner、迁移策略，以及是否采用临时 Dock。
- 仍未验证：临时 Dock 对产品身份的影响、持久 `dismissed` 的安静入口应放在哪里、宿主选择是留在面板内还是下钻设置。需要真机与用户测试。

### 2.11 宿主检测与无宿主兜底（2026-10-22 决定）

**事实来源**：首启不新增扫描器，只消费现有宿主快照。

- `HostIntegrationManager.refresh()` 会对 `HostID.productVisibleCases` 并行 `inspect`；每个宿主返回带 `availability` 的 `HostIntegrationSnapshot`（[HostIntegrationModels.swift:411](<../helper/Sources/ClaudioCore/HostIntegrationModels.swift:411>)、[HostIntegrationManager.swift:646](<../helper/Sources/ClaudioCore/HostIntegrationManager.swift:646>)）。
- `HostAvailability` 三态：`.available`、`.notInstalled`、`.unavailable(reason:)`。设置页已经用 `IntegrationAutomaticState.notInstalled` 把它们显示为「未安装」。
- 检测方式因宿主而异：Claude Code / Codex 探测 CLI 与版本；WorkBuddy 校验应用 bundle 身份；OpenCode / Kimi Code / Grok Build 校验 CLI 版本、配置根和发布准入。
- 覆盖率来自 `HostSourceRowPresentation.supportedCount / totalCount`，不能写死「5/5」。
- 连接和自动维护仍由 `HostIntegrationManager` 与 intent 决定；首启只筛选和呈现，不另写连接策略。

**首启筛选规则**

| 快照事实 | 首启处理 |
|---|---|
| 仍在首次刷新 | 显示「正在检查已安装的宿主…」，不断言没有宿主 |
| `available` 且至少一个可听事件 | 列入可连接短列表，显示宿主名与覆盖率 |
| `available` 但可听事件为 0 | 不列入可连接；设置页解释能力限制 |
| `notInstalled` | 首启隐藏；设置「连接」页显示「未安装」 |
| `unavailable(reason:)` | 不提供连接；若它是唯一检测结果，显示「检测到但需要处理」并深链设置 |
| 已有真实事件 | 直接显示已接上状态；已有配置/回执的用户不重放首启 |

**多宿主规则**

- 首启最多显示 4 个已检测到的宿主（2×2 紧凑列表）；超过 4 个显示「查看全部」。
- 完整宿主目录、未安装状态、能力限制、重新检测和诊断全部留在设置「连接」页；首启不是第二个目录 owner。
- 使用 `productVisibleCases`，不使用 `allCases`；AX Beta 和未发布候选不进入首启。
- 宿主按钮必须显示真实覆盖率；Codex 4/5、OpenCode 2/5 等不能显示成 5/5。

**无宿主状态**

> 还没检测到可连接的宿主<br>
> 示例试听仍然可用；事件声音要等接上宿主后才会响。<br>
> [打开连接设置] [稍后再说]

- 不阻塞、不伪造已安装或已连接；示例试听仍可用。
- 主操作进入设置「连接」页；那里有完整列表、「未安装」原因和「重新检测」。
- 「稍后再说」只收起清单，写 `dismissed` / `seen-without-host`，不写 `completed`；重启和升级不重放整套首启。
- 面板底部或设置页保留安静入口「未连接宿主 · 连接」。
- 以后检测到新宿主时，只更新这个入口或显示「检测到 X」，不重新弹整段首启。

**边界**

- 检测到等于「已安装且版本兼容」，不等于用户正在使用，也不等于已接入。
- 如果宿主装在非常规路径导致没检测到，设置页的「重新检测」和原因文案是兜底，不在首启里做手动路径选择。
- 原生原型中的宿主列表与覆盖率是 fixture；正式实现必须从快照生成。

## 3. §3 设置信息架构（讨论中）

### 3.1 现状证据

- `SettingsDestination` 固定为八个 raw value：`events-and-sounds`、`sounds`、`integrations`、`notifications`、`general`、`shortcuts`、`usage`、`about`。
- 侧栏分三组：
  - primary：默认组／工作区、声音、集成、通知；
  - advanced：通用、快捷键；
  - product：活动与诊断、关于。
- ADR 0008 / 0022 固定了唯一 retained 设置窗口、八页、typed route、窗口期导航历史与焦点 handback。
- 面板与集成页使用稳定 raw value 进行深链；快捷键页在 v1 删除前同样使用稳定路由。historical `display` route 会投影到「通用」。
- 用户可见名称已经将「默认组／工作区」改为「工作区」，但内部术语仍大量出现在页面标题、状态与诊断中。
- 2026-10-22 决定：v1 不启用全局快捷键，`shortcuts` 目的页从侧栏移除；旧路由的迁移方式待实现时确认。

### 3.2 用户问题

- 现状八页等权并列，使「通知」「快捷键」「关于」与核心的「工作区」「声音」「集成」争夺注意力；v1 还会删除快捷键页。
- 用户任务通常是「让某个项目的声音正确」或「确认某个宿主接上了」，而不是「进入通知目的页」。
- Surface、Binding、Receipt、当前激活等词汇在主界面出现时，用户需要先学习 Claudio 的内部模型。
- 「活动与诊断」是低频但高价值的排障面，放在顶层侧栏会鼓励用户先看统计，而不是先看最近一次事件。

### 3.3 约束

- 不得破坏现有 raw value、深链与窗口期历史；页面隐藏或合并必须保留旧路由的可达性或明确迁移。
- 不得创建第二个设置窗口或第二套路由 owner。
- 任何页面合并都需要 ADR 修订，并同步 DESIGN.md、PLAN-SETTINGS-EXPERIENCE.md 与验收文档。
- 侧栏顺序、分组与标题变更会影响键盘、VoiceOver 与焦点恢复，必须重新走查。

### 3.4 可选路径

以下三种路径保留为早期权衡记录；2026-10-22 已收敛到 6 页 / 5 页两个原型变体。

| 方案 | 描述 | 风险 | 适用阶段 |
|---|---|---|---|
| A. 只重分组 / 降权 | 保留现有页面与 raw value；只调整显示名、顺序与分组 | 低 | 历史选项 |
| B. 隐藏低频页，保留路由 | 侧栏只显示 5 页左右；低频页通过上下文入口与深链到达 | 中 | 历史选项 |
| C. 合并目的页 | 通知并入工作区，快捷键并入通用，活动与诊断改为下钻，关于移入应用菜单 | 高 | 历史选项 |

**2026-10-22 决定**：本轮按 5–6 页目标出讨论原型，不直接改生产实现。已绘制 6 页与 5 页两版：6 页版把「诊断」作为顶层；5 页版把「诊断」改为从「连接」与「最近事件」下钻。推荐先以 6 页版做走查，再根据真实使用频率决定是否收起诊断页。

**2026-10-23 收敛**：先走 6 页，5 页暂缓；6 页采用工作区 / 声音包列表→详情、提醒与静音、活动与诊断保留顶层。详见 §3.11。

**建议的 6 页结构（讨论稿）**

| 新页面 | 保留 raw value | 内容 | 旧页面 / 迁移 |
|---|---|---|---|
| 工作区 | `events-and-sounds` | 默认组、工作区规则、五事件、目录与来源 | 原「工作区」；仅显示名与层级调整 |
| 声音 | `sounds` | 声音包、事件映射、AI 提示音、生成记录 | 原「声音」 |
| 连接 | `integrations` | 宿主产品与来源、连接、回执摘要、诊断入口 | 原「集成」 |
| 安静与提醒 | `notifications` | 动态静默、事件动画、提醒行为 | 原「通知」；建议改名 |
| 通用 | `general` | 语言、登录项、更新、关于入口 | 原「通用」+「关于」 |
| 诊断 | `usage` | 活动摘要、最近事件、诊断日志 | 原「活动与诊断」；5 页版改为下钻 |
| — | `shortcuts` | v1 删除 | 快捷键模块移除 |

**路由兼容**：

- 保留 `events-and-sounds`、`sounds`、`integrations`、`notifications`、`general`、`usage` 六个 raw value。
- `shortcuts` 在 v1 删除；旧持久化值不得导致启动失败。可选做法：保留 raw value 并重定向到 `general`，或做一次性迁移后移除 enum case。前者风险更低。
- `about` 改为「通用」页内的关于 sheet；旧 `about` 深链重定向到 `general` 并打开该 sheet。
- 历史 `display` → `general` 的现有迁移继续保留。

### 3.5 术语下沉建议

主界面只回答「当前是什么、我能做什么」：

- 用「Claude Code 已连接 · 5/5 声音可用」替代「当前激活 / 回执 / Binding」。
- 用「声音来源」替代主界面中的「Surface」。
- 把「安装身份」「回执代次」「binding 覆盖」「配置来源」收进诊断详情。
- 保留内部术语在 ADR、诊断页与开发者文档中，不为 UI 重命名领域模型。

### 3.6 待讨论问题

1. 「安静与提醒」这个名字是否准确？它目前承接动态静默与事件动画，是否还应包含其他提醒行为？
2. 6 页 vs 5 页：诊断值得一个顶层入口，还是只从「连接」与「最近事件」下钻？
3. 「关于」收进「通用」页内的 sheet 是否可接受？还是保留一个低权重的顶层入口？
4. 设置窗口内的搜索是否作为本轮配套？如果要隐藏低频页，搜索是重要的发现性兜底。
5. `shortcuts` 删除：保留 raw value 并重定向到 `general`，还是彻底移除 enum case 并做一次迁移？前者更稳。
6. 是否同意先只改显示名、顺序、分组与术语，不动 raw value 与深链？这是最低风险的第一步。
7. 两类诊断如何分离：`integrations` 内的宿主连接诊断（安装身份、配置来源、回执、能力证据）与 `usage` 的活动/日志诊断是否继续各自保留？5 页版不能把前者伪装成后者。
8. 6 页 / 5 页 HTML 的目标是 IA 走查还是功能规格？若作为功能规格，必须先补齐 §3.9 的缺口并移除未经实现的新增项。

**结构性错位（必须先修）**

1. **`连接` 页的「查看诊断」指向了错误的目的地。** 生产的宿主诊断回答「这个宿主为什么没接上 / 能力证据是什么」，`usage` 回答「今天触发了多少、日志里有什么」。5 页版若把宿主诊断藏进 `usage`，会把两个事实 owner 混在一起。
2. **`诊断` 页画的是未来功能。** 「最近事件 + 为什么没响 + 播放结果」是 Backlog，当前 `ActivityDiagnosticsView` 没有这些字段；不能用它声称「所有现有功能已覆盖」。
3. **「最近事件」入口不存在。** 面板只有「最近通知」（待响应记录），生产没有「最近事件」页面；5 页版下钻入口必须改为真实存在的位置，例如面板最近通知、连接页或关于页。

**跨页 / 壳层缺口**

- 深链失败态、失效目标 fail closed、窗口期导航历史、焦点回退、侧栏键盘顺序与 VoiceOver 标题未在原型中表达。
- 原型所有宿主、覆盖率、连接数、回执时间均为固定演示值；生产必须来自 `HostIntegrationSnapshot` / `HostSourceRowPresentation`，不得硬编码。
- 设置搜索不是生产能力，已标注讨论项；若因 5 页隐藏诊断而引入搜索，需先决定它是否进入本轮范围。
- `shortcuts` 删除是有意差异，不算缺口；但 enum、持久化值与深链迁移仍需单独决定。
- 页面显示名改动（集成 → 连接、通知 → 安静与提醒、活动与诊断 → 诊断）都需要本地化目录同步，并确认不会与现有术语冲突。

**使用建议**

- 本轮 IA 走查仍可用 6 页版，但结论只能落在「页面归属、顺序、命名、入口」；不要据此验收页内功能完整性。
- 若要把原型当实现规格，至少先完成：修正两类诊断归属；把 `usage` 页替换为生产内容；为工作区 / 声音 / 连接补齐操作与失败态；明确关于 sheet 的内容与路由；移除或明确标注所有未实现的新增项。

### 3.12 2026-10-23 二次复核修订（仅 HTML）

第二轮复核确认 6 页 IA 可作为下一步基线，并修复六类操作语义与状态表达问题。

- **AI 表单改为窗口附属表单，并拆成四个互斥状态**：未生成 / 生成中 / 已保存 / 保存失败。未生成时只有“生成 3 个候选”；生成中只显示进度与“取消生成”；已保存时显示候选，当前选用上下文有效才允许“用于此事件”；保存失败时只允许试听、重试保存或丢弃，`用于此事件` 禁用，且不提供新生成。遵循 [ADR 0026](../docs/adr/0026-retain-generated-audio-in-local-history.md)：关闭 / Esc 只收起表单，应用运行期间同一生成继续，重开读取实际状态，不重置计时或重复请求；关闭结束旧选用上下文，历史音频须从当前事件重新明确选用。取消生成只停止本地等待，回到描述并保留输入，不承诺远端停止生成或计费。
- **保存失败持续阻止新生成**：结果保留在生成记录顶部“待处理”区域，显示未保存原因、实际音频数量、试听和重试保存。表单与记录页读取同一任务；关闭、离页、切换包 / 事件不丢弃结果，也不解除限制。重试仅保存当前结果，不重新生成；保存成功后转入已保存记录，不自动采用。丢弃先显示仍未保存的实际数量并确认移到废纸篓，取消保留结果；保存或明确放弃前持续禁止新生成，已保存记录和声音包不受影响。生产移到废纸篓失败时保留剩余结果及限制，不得降级为永久删除；HTML 只演示确认与内存状态，不证明文件操作成功。
- **HTML 表单使用真正的模态 `dialog`**：以 `showModal()` 阻止背景交互，覆盖 Tab / Shift+Tab 首尾循环；关闭按钮与 Esc 都归还焦点到触发的事件来源菜单。后台完成不抢焦点、不自动打开表单或选用结果。原生附属表单的焦点与 VoiceOver 仍须单独验证。
- **保存失败由场景选择复现**：`失败` 场景下生成会停在保存失败；`重试保存` 恢复为已保存，用于验证恢复路径。生产实现需要把这个状态机接到真实候选与写入回执，而不是只在前端模拟。
- **空态补齐直接动作**：连接空态提供“重新检测”并回显检测结果；声音库空态提供“恢复全部内置包”；活动与诊断空态提供“打开连接”，不再只给下一步说明。
- **工作区事件动作改为按修改范围命名**：用户包显示“编辑包内声音…”，内置包显示“查看包内声音…”。动作进入对应声音包并定位事件行，同时显示“来自工作区 … › 事件”与返回工作区入口；共享影响提示只留在真正发生修改的包详情。
- **工作区与声音包共用一份演示数据**：列表摘要、详情、事件行、可用按钮和计数均由同一对象生成。默认组 5/5 且详情五个开关全开；`my-cues` 3/5 且详情恰有两个未配置事件；`focus-set` 5/5；工作区适用来源数量也由勾选状态推导。不再出现摘要与详情互相矛盾。
- **连接状态补齐“现在该做什么”**：OpenCode 开关关闭时摘要写“已关闭”，不再写“尚未收到事件”；Grok 改为“配置已写入 · 等待重启”，并在宿主体内单独显示“重启后验证 · 未验证”，不把重启后结果提前写成已生效。
- **评审说明移出窗口**：窗口内删除“列表进入详情 / 不在声音页内增加第二层侧栏”“旧 about 深链”“fixture 演示数据”等说明；这些内容移入设置窗口外的“评审备注”。声音包的共享影响提示从三处收敛为包名下一处；工作区的“独立保存 / 不继承”重复说明删除。

## 4. §2 最近事件 / 为什么没响（Backlog）

### 4.1 问题

面板目前回答「我能调什么」，但不回答「刚才发生了什么、为什么没声音」。用户需要在宿主、集成、活动、日志之间跳转，才能定位一次静默。

### 4.2 建议

在面板顶部增加一条 **最近事件**：

- 来源、事件、时间、结果（播放 / 静音 / 无映射 / 组音量为零 / 动态静默 / 播放失败）。
- 点开显示决策链：收到回调 → 映射 → 事件开关 → 组音量 → 动态静默 → 播放结果。
- 只消费现有 receipt、activity 与 config 投影，不新增事实 owner。
- 默认只显示最近一条；需要时下钻到最近 N 条。

### 4.3 边界

- 不保存 prompt、response、项目路径、会话内容或音频绝对路径。
- 区分「没有回调」与「有回调但没播放」，不能把两者合并成「没声音」。
- 不能从最多 20 条 receipt history 或日志反推活动摘要。

## 5. §4 声音质量与播放语义（Backlog）

### 5.1 建议

- 建立 pack lint：时长、峰值 / RMS、首尾静音、频谱相似度、事件间可辨性。
- 在低音量、单耳、嘈杂环境下走查五个事件是否仍可区分。
- 明确事件风暴与重叠策略：多个子任务连续结束时，声音是排队、合并还是打断。
- 明确试听与自动播放的音量语义差异：声音页试听跟随系统输出音量，面板 / 组详情使用组音量。至少在试听控件旁显示当前语义，避免「试听正常、事件没声」的误判。

## 6. §5 渐进披露（Backlog）

### 6.1 工作区规则试算器

增加「选择文件夹 → 显示将命中的规则 / 包 / 音量 / 来源」的只读试算器。它不写配置，只解释当前解析结果。

### 6.2 AI 提示音收窄

若 v1 的目标是「声音中心」，建议把 AI 提示音收成「描述 → 试听 → 用于事件」；provider、凭据、生成记录与候选政策收进高级入口，避免与核心声音闭环争夺导航权重。

## 8. §7 验证方式（Backlog）

建议用三个可测指标组织走查：

1. 首次听到声音的时间。
2. 首次成功接入的时间。
3. 从「没响」到定位原因的时间。

找 5 个真实用户走一遍，记录卡点；不做网络遥测，保持本地优先。UI 变更的验收继续区分自动 harness、原生键盘 / VoiceOver、真实宿主回调与发布证据。
